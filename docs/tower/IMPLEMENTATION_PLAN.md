# Коллекционный журнал NIS: технический план и чек-лист

Обновлено: 24 октября 2026 года, редакция 4. Работают доступ, кошелёк, ручные и автоматические награды, паки, личная коллекция и настройка внешности. Этапы 5–7 завершены; этап 9 частично готов: магазин и снимки аватарки реализованы, общий профиль класса и присутствие остаются отдельными этапами. Оптимизация портретов и production-домен CDN по-прежнему относятся к незавершённой части этапа 2.

Актуальный цикл: учебное достижение → нишкойны → пак → фрагменты → карточка в журнале. Персонажи — коллекционные изображения в школьной форме NIS; у них нет игровых характеристик и способностей. Кастомизация существующей геометрической аватарки остаётся отдельной частью.

Этот файл — основной трекер работы. Этап считается завершённым только после выполнения его критериев приёмки. При реализации отмечать `[x]`, записывать дату, миграции и фактически выполненные проверки в журнал в конце файла. Изменения согласованного состава фиксировать здесь, а не только в переписке.

## 1. Состав первой версии

- Главный экран — адаптивный коллекционный журнал, рядом разделы паков, кошелька и аватарки. Башня может остаться декоративным фоном; интерактивный интерьер не требуется.
- Нишкойны за учебные достижения, кошелёк и история операций.

- Все карточки одного размера: 9 в высоту × 6 в ширину, вертикальный формат 2:3. Мастер иллюстрации 1200×1800 px; CSS-оболочка `aspect-ratio: 2 / 3`.
- Фрагменты конкретных героев; сборка; универсальные осколки за избыток фрагментов.
- Магазин фиксированных аксессуаров и несколько готовых оформлений профиля.
- Постоянная выбранная фигурка и аксессуары в существующих игровых модулях.
- Фигурки присутствующих учеников на блоках модулей и переход в профиль.
- Доступ только для включённых классов; управление только для назначенных администратором учителей.

Из текущего состава удалены экспедиции, бои, команды персонажей, боевые характеристики, трофеи и редактор комнаты. Для них не оставлять заготовки моделей, API, кнопок, сцен или промптов. Торговля, переводы валюты, реальные платежи и отдельная авторизация также не входят в состав.

## 3. Архитектура

Игра размещается на `https://dbug.ink/tower/`. Управление: `/teacher/tower/`. API: `/api/tower/` и `/api/teacher/tower/`.

Новый Django app `tower` внутри текущего проекта, одна существующая БД и действующие сессии. PostgreSQL хранит игровой прогресс и операции, но не байты изображений. Отдельный сервис и отдельная БД на старте не нужны.

Предлагаемые модули:

```text
tower/
  models/                 # access, economy, collection, cosmetics
  permissions.py          # единые проверки доступа и области классов
  services/               # wallet, rewards, packs, collection, assets
  views/                  # student, teacher, journal, profile, presence
  urls.py
  admin.py
  templates/tower/
  static/tower/           # CSS, JS и небольшие служебные SVG
  content/                # версионируемые JSON-каталоги без больших изображений
  management/commands/    # импорт, проверка ассетов, сверка кошельков
  tests/
```

В `core` остаются небольшие изменения: поля доступа, подключения к результатам, ссылки в интерфейсе, расширение фигурки. Игровую логику не дописывать в большой `core/views.py`.

## 4. Изображения вне основной БД

### Рекомендуемый вариант

Cloudflare R2 Standard + собственный домен ассетов, например `assets.dbug.ink`. Это рекомендуемая инфраструктура, ещё не созданный и не проверенный домен. Сначала проверить, где управляется DNS: для прямого подключения R2 custom domain зона должна находиться в том же аккаунте Cloudflare. Если перенос DNS не подходит, использовать другое S3-совместимое хранилище с CDN и тем же контрактом путей.

```text
Браузер -- HTML / JSON --> Django -- данные --> PostgreSQL
Браузер -- изображения ---------------------> CDN / R2
Оператор -- загрузка подготовленных файлов -> R2
```

В БД хранится `asset_key` вида `tower/v2/cards/nis-coder.a18c2f.webp`, размеры, MIME-тип, контрольная сумма и при необходимости описание для доступности. URL строится через `TOWER_ASSET_BASE_URL`; домен не зашивать в записи персонажей. Идентификаторы контента стабильны, хеш имени меняется при замене изображения. `v2` обозначает новый художественный комплект, а не уже выполненную загрузку.

Нельзя сохранять PNG/JPEG, base64 или data URL в JSONField/TextField/BinaryField. Небольшие строки метаданных всё равно занимают немного места в БД; объём самих картинок туда не попадает.

### Разделение файлов

| Тип | Где хранить |
|---|---|
| Исходные изображения высокого качества | Локальный архив с резервной копией или отдельный закрытый bucket |
| Оптимизированная игровая графика | Отдельный публичный bucket R2, только художественные ассеты |
| CSS, JS, небольшие SVG | Репозиторий и WhiteNoise |
| Манифест ассетов | Версионируемый JSON в репозитории; сервер возвращает нужные URL в игровом API |
| Данные учеников, оценки, баланс | Только авторизованные API и БД, никогда в публичном bucket |

Публичная ссылка на рисунок доступна любому, кто её получил. Это не даёт доступа к игре, коллекции или начислениям. Ограничение игры по классам относится к страницам/API; скрывать обычные иллюстрации за авторизацией для MVP не требуется.

### Поставка ассетов

1. Генерация по ART_PROMPTS.md, проверка единого стиля и альфа-канала.
2. Сохранение оригинала; экспорт WebP, уменьшенных копий и при необходимости PNG с альфой.
3. Запись asset ID, пути, размеров, checksum, роли и safe-area в манифест.
4. Проверка имён, форматов, габаритов, размера и полного комплекта до публикации.
5. Загрузка нового набора в `tower/v2/...` ограниченным ключом только к bucket игры.
6. Публикация версии каталога только после проверки наличия всех ссылок.
7. `Cache-Control: public, max-age=31536000, immutable` только для файлов с неизменяемыми хешированными именами.
8. Старые файлы сохранять до окончания срока использования предыдущей версии; откат переключает каталог, а не удаляет картинки.

В первой версии достаточно загрузки оператором через CLI/панель R2; ключи записи приложению и браузеру не нужны. Если позже появится загрузка из админки — отдельный backend через `STORAGES['tower_assets']`, валидация и ограниченные серверные ключи. Не заменять `default` storage платформы без необходимости.

Для разработки — тестовые ассеты в локальной файловой папке вне БД. В production не сохранять загруженные файлы на обычном диске веб-сервиса Render: изменения его временной файловой системы не переживают перезапуск/деплой. Google Drive с учебными работами не использовать как CDN игры.

### Размеры и производительность

- Необязательный декоративный фон: мастер 1920×1080; web-копия 1280×720; цель до 400 КБ. Для журнала достаточно CSS-фона, генерировать комнату не требуется.
- Карточка: непрозрачный мастер PNG 1200×1800; web-копии 600×900 и 240×360. У всех одинаковый формат 2:3; цель до 100–250 КБ для средней копии.
- Аксессуар: мастер 512×512 с альфой; web-копия 128/256 px; цель до 30–60 КБ.
- Бюджет первой загрузки журнала: до 2 МБ изображений; в сетке использовать миниатюры, крупные картинки догружать при открытии карточки.
- Это цели экспорта, а не гарантия размера от генератора; уменьшение и проверка после генерации обязательны.
- Манифест выдаётся Django, поэтому браузеру не нужен внешний `fetch` JSON. Для обычного `<img>`/CSS-фона CORS обычно не нужен; для будущего Canvas/экспорта добавить разрешение только нужных origins и проверить CSP.

По тарифам R2 на дату документа Standard имеет бесплатную квоту 10 GB-month, 1 млн операций класса A и 10 млн класса B в месяц; исходящий трафик R2 не тарифицируется. Это не обещание бесплатной эксплуатации: учитывать запросы, другие продукты Cloudflare и общий объём аккаунта. Для production использовать custom domain, а не ограниченный `r2.dev`.

## 5. Права доступа

### Независимые переключатели

1. `Teacher.can_manage_tower = False`. Меняет только Django superuser через `/admin/`; обычный staff и учитель не могут назначить право себе или другому.
2. `ClassGroup.tower_enabled = False`. Меняет superuser либо назначенный учитель только для собственного обычного класса.
3. Глобальный `TOWER_ENABLED = False` при первом деплое. Позволяет включить пилот и быстро остановить игровую часть.

При миграции все новые разрешения выключены. Обычные PATCH/импорт/массовое редактирование Teacher/ClassGroup не должны обходить специальные проверки.

### Эффективный доступ ученика

```text
глобально включено
И действующая сессия активного Student
И Student не гостевой / не арендованный
И существует его основной класс ИЛИ подтверждённое дополнительное членство, где:
    класс обычный, tower_enabled=True
    владелец существует, активен, can_manage_tower=True
```

Класс для проверки берётся из БД, а не из `student_selected_class_id` или запроса. Ученик с несколькими разрешёнными классами имеет один игровой аккаунт, кошелёк и коллекцию. Стандартный основной класс учитывать вместе с таблицей членств, с устранением повторов.

Отключение класса/права учителя действует со следующего запроса. Если другой разрешённый класс у ученика остался, доступ сохраняется. Коллекция, кошелёк и выбранные украшения не удаляются; при восстановлении доступа продолжается прежний прогресс. Долгоживущие флаги в сессии не считаются источником разрешения.

### Область полномочий

| Аккаунт | Игра | Управление |
|---|---|---|
| Django superuser | Административный предпросмотр | Назначение учителей, классы, общий каталог, версии и аудит |
| Назначенный активный учитель | Предпросмотр без личного ученического кошелька | Свои классы, их награды, выдачи с причиной и журнал операций |
| Обычный учитель | Нет | Нет игровых разделов и API; существующие инструменты урока работают |
| Ученик разрешённого класса | Свой прогресс | Нет учительских действий |
| Остальной ученик / гость | Нет | Обычный интерфейс платформы |

Для общего каталога карточек, вероятностей и магазина редактором остаётся superuser: настройка одним учителем не должна менять экономику других классов. Назначенные учителя управляют доступом и наградами в своих классах.

Проверки применяются к HTML, всем API, присутствию, профилям и начислениям. Без входа API возвращает 401; без права — 403; чужие объекты скрываются 404. Для отключённых аккаунтов не показывать баланс, магазин, игровые украшения и игровые пункты меню. При отключении аккаунт отображается стандартным способом; сохранённые украшения снова доступны после включения.

Стартовые каталоги импортируются командой идемпотентно по стабильным slug; повторный импорт не выдаёт награды и не создаёт новые копии героев. Миграции создают схему и безопасные defaults, а не загружают изображения.

## 7. Кошелёк и награды

Все изменения кошелька, коллекции и покупок проходят через сервисы. В транзакции PostgreSQL блокируется кошелёк/игрок, проверяется доступ, уникальность операции и остаток, создаются проводки и результат. Цена, выпадения и величина награды вычисляются на сервере.

Реализация этапа 3: один кошелёк на аккаунт ученика, общий для основного и дополнительных классов. Перед ленивым созданием игрока/кошелька блокируется существующая строка Student, затем Wallet; этот же порядок использует команда сверки. Целые остатки ограничены диапазоном 0…9 007 199 254 740 991 (точное число в JSON браузера), отрицательный баланс запрещён CHECK-ограничениями БД.

Учитель выдаёт только положительные целые нишкойны ученикам своего включённого класса, с причиной длиной 1–240 символов. Лимит одной ручной выдачи задаёт `TOWER_MANUAL_AWARD_LIMIT` (по умолчанию 10 000). Новый UUID означает отдельную сознательную ручную выдачу; автоматические события с однократностью по учебному результату появятся на этапе 4. Интерфейс выдачи: `/teacher/tower/wallets/`. Ученик видит свой баланс и историю на `/tower/`; API чтения — `/api/tower/wallet/`. История загружается страницами по 25 операций, список учеников — по 50.

Суперпользователь видит кошельки, проводки, запросы и аудит в `/admin/`. Поля баланса и записи истории доступны только для чтения. Из карточки кошелька отдельная форма «Корректировка с записью в журнал» добавляет положительную или отрицательную проводку с причиной, UUID и лимитом `TOWER_ADMIN_ADJUSTMENT_LIMIT` (по умолчанию 1 000 000 по модулю). Обычный staff не имеет доступа к этим моделям, даже с назначенными Django permissions. Изменение и удаление проводок/аудита запрещены через модели, queryset и интерфейс администратора; прямой SQL владельца БД остаётся вне этой защиты.

Учитель видит общий остаток ученика, но из истории — только собственные начисления в выбранном классе. Ученик видит все свои операции, включая административные корректировки. История и игровой аккаунт защищены от каскадного удаления; при наличии связанных записей API удаления ученика/класса возвращает 409. Для сохранения истории используется деактивация аккаунта. Выключение доступа сохраняет баланс.

`spend_coins` — внутренний сервис для будущих покупок, публичного API списания произвольной суммы нет. На этапе паков покупка и выдача содержимого должны выполняться в одной общей транзакции, с серверной ценой.

Команда `python manage.py reconcile_tower_wallets` сверяет суммы обеих валют и каждый промежуточный остаток с проводками. Она ничего не исправляет: несоответствие завершает команду с ошибкой. Запускать после деплоя и перед пилотом; исправления проводить отдельной обоснованной операцией.

Повтор запроса после потери соединения возвращает сохранённый результат; тот же ключ с другим телом — 409. Уникальный request_id защищает покупку от повторов, а уникальный event_key — учебное начисление: новый request_id не позволяет повторно получить учебную награду. При необходимости две защиты используются вместе.

### Источники и область начислений

- Награду можно настроить только для собственного занятия/модуля учителя и собственного включённого класса, которому назначено это занятие. Модуль из общей библиотеки сначала клонируется.
- Для квиза/кодинга определить один серверный контекст класса из пересечения доступных классов ученика, назначения занятия и активных правил автора занятия. Если допустимы несколько — явный выбор из проверенного сервером списка, затем фиксированный контекст. Не складывать награды нескольких классов за один task/quiz.
- При выполнении учеником урока другого неназначенного учителя награды не начисляются, даже если ученик имеет доступ к башне через другой класс.
- Копирование урока не активирует скопированные правила автоматически.
- Новые правила применяются только к результатам после включения. Массового начисления за старую историю в MVP нет.
- На момент события и записи награды проверяются допуск ученика, право учителя и принадлежность источника. Отзыв разрешения прекращает новые начисления.

### Правила MVP

| Источник | Момент выдачи | Ключ уникальности |
|---|---|---|
| Кодинг | Первое сохранённое ACCEPTED для task при активном правиле | `coding:student_id:task_id` |
| Квиз | Первое достижение заданного порога; повторные попытки разрешены, повторная выдача нет | `quiz:student_id:module_id` |
| Призовое место | Однократная фиксация наградного результата завершённого раунда | `game:student_id:round_id` |
| Ручная выдача | Назначенный учитель, свой класс, положительная сумма в заданном лимите, обязательная причина | ID однократной операции |

Изменение версии RewardRule или принадлежности классу не сбрасывает ключи task/quiz. Стартовая команда не выдаётся. Возможный одноразовый ознакомительный пак отдельно определить при реализации паков; автоматически выдаваемые персонажи не являются условием работы журнала.

Для игровых модулей учесть естественное завершение гонки, финал турнира, нормальный исход «Поля чудес», ручную остановку и досрочное завершение. Ручная остановка без подтверждённого итогового результата не награждается. В «Поле чудес» нет обычной таблицы мест: отдельная явно выбранная награда за командную победу; недоступные поля мест не показывать. Для турнира MVP награждает только достоверно определённые места; не придумывать третье место без правил его определения. Учитель видит предварительный список выдач перед ручной финализацией.

Не использовать только `transaction.on_commit()` без надёжной очереди: падение процесса между commit и callback потеряет начисление. Для компактного MVP результат урока и выдачу записывать в общей транзакции, после внешнего judge-запроса. Короткие блокировки, без сети внутри. Добавить команду сверки/восстановления пропущенных выдач по сохранённым результатам и времени активации правила; повтор безопасен по event_key.

История проводок не редактируется; исправления отдельной компенсирующей проводкой с причиной, только superuser. Если списание корректировки сделает баланс отрицательным, автоматическую операцию отклонить и разобрать вручную. Учитель не может списывать деньги или редактировать баланс напрямую. В учительском журнале показывать свои источники, а не чужие учебные результаты ученика.

## 8. Паки и коллекция

Стартовое предложение: пак стоит 50 нишкойнов, содержит 3 слота по 2 фрагмента; сборка любого героя требует 10 фрагментов. Вероятности слота: обычный 70%, редкий 22%, эпический 7%, легендарный 1%; герой внутри редкости выбирается равновероятно. Это данные опубликованной версии, не константы в JS.

Защита: после четырёх паков подряд без редкого или лучше в следующем один слот гарантированно редкий+. Для гарантированного слота веса распределяются между rare/epic/legendary пропорционально 22:7:1; сброс счётчика и точные правила показывать в справке. Вероятности гарантированного слота отличаются от обычного.

Покупка сразу сохраняет списание, все выпадения и изменения коллекции одной транзакцией. Анимация только показывает уже определённый результат; закрытие вкладки ничего не теряет и повтор открытия не меняет выпадения. Не создавать отдельную возможность «перебросить» результат после просмотра.

При достижении порога персонаж автоматически собирается и открывается как постоянная карточка в журнале. Лишние фрагменты превращаются в универсальные осколки по коэффициенту версии каталога, первоначально 1:1. Универсальные осколки обмениваются на недостающие фрагменты выбранного персонажа по заданной цене редкости. Покупки и сборка конкурентно безопасны. Редкость влияет на коллекционную ценность и выпадение; игровую силу не вводить.

До пилота проверить ожидаемое число паков на героя и время сбора каждой редкости моделированием экономики. Отдельный лимит гарантии легендарного героя не обещать, пока не выбран и не проверен баланс.

## 9. Коллекционный журнал и формат карточек

Сетка одинаковых вертикальных карточек 2:3; формулировка «9 на 6» принята как высота 9 и ширина 6. Размер изображения и размер внешней карточки одинакового отношения сторон. Пример: 120×180 CSS px в сетке, 300×450 px при увеличении; на телефоне сетка адаптируется без растягивания рисунка.

Иллюстрации непрозрачные и уже содержат персонажа с простым цветным фоном. Рамка редкости — отдельное сгенерированное изображение с альфа-каналом, накладываемое поверх портрета. Имя, звёзды, прогресс фрагментов и отметка «Новая» остаются отдельными HTML/SVG-слоями; подписи не меняют высоту карточки. Обычная: серебро, 2 звезды; редкая: синий, 3; эпическая: фиолетовый, 4; легендарная: золото, 5. Звёзды обозначают редкость, не боевой уровень. Применять единый `aspect-ratio: 2 / 3`, одинаковые скругления и safe-area. Для 9×6 см при печати размер задаётся отдельно.

Карточка показывает оригинального персонажа-школьника NIS в объёмной мультяшной стилистике, ориентированной на референс Supercell. Форма: тёмно-синий пиджак, белая или соответствующая фото тёмная рубашка, красный либо зелёный галстук с диагональными полосками. Фото NIS использовать как референс формы, а не как набор лиц для воспроизведения. Единый художественный контракт и 12 индивидуальных промптов — в ART_PROMPTS.md.

Состояния: не обнаружена (силуэт), собирается (виден персонаж и N/10), собрана (полная карточка). Фильтры по редкости/получению, общий счётчик коллекции, увеличение и биография при нажатии. Собранные карточки можно выбирать избранными для профиля. При нажатии не открываются управление отрядом, навыки или выбор маршрута.

## 10. Аватарка, профиль, присутствие

- Форма выбирается из существующих пяти, цвет — из валидированной палитры. Для допущенного игрока выбор постоянный.
- Три слота: голова, очки, усы. Предметы из одного слота взаимоисключаются.
- Аксессуары рисуются на общей сетке; привязки и масштаб корректируются для каждой формы. Не вырезать фигурку целиком вместе с аксессуаром.
- В игровой раунд сохранять снимок внешности, чтобы смена парика не меняла уже завершённую гонку. Для текущего присутствия использовать актуальный loadout.
- У недопущенных аккаунтов сохраняется обычное поведение платформы; меню и магазины башни не появляются.
- Публичная внутри разрешённого класса карточка: аватар, оформление, избранные герои, достижения. Ни баланс, ни детальные оценки/код не выдаются одноклассникам.
- Полная учебная аналитика — владельцу; учителю только в пределах существующих разрешённых классов и источников. Существующие проверки учительского профиля сохраняются.
- Присутствие: heartbeat раз в 25–30 секунд только из видимой вкладки модуля; запись считается устаревшей через 90 секунд. Закрытие вкладки не требует надёжного unload-запроса.
- Область присутствия — конкретные session + class + module. Учитель читает только свою группу урока, ученик — одноклассников в доступном контексте. Проверять реальный тип/ID модуля и допуск к уроку.
- При нескольких вкладках действует последняя активная; сохранять идентификатор вкладки/сессии и проверять устаревшие обновления. Показывать до 6 фигурок, остальные под «ещё N».
- Чтение группировать одним запросом, не делать запрос на каждую карточку модуля. Не вводить WebSocket для этой задачи.

### Проверки этапов

- Доступ: superuser / staff без права / назначенный учитель / обычный учитель / свой и чужой класс / несколько членств / owner=None / отключённый владелец / гость / отозванное право в открытой вкладке.
- Исключение обходов: прямой URL, API без меню, массовый импорт, подмена class_id, отправка can_manage_tower через обычный PATCH, доступ к чужому player/run/profile.
- Экономика на PostgreSQL: параллельные покупки, два одинаковых события, один ключ с разным телом, недостаток средств, сбой транзакции, повтор команды сверки. SQLite не подтверждает поведение блокировок PostgreSQL.
- Учебные источники: повтор квиза после порога, повтор ACCEPTED, смена правила и класса, автоматический/ручной финал, остановка игры, несколько разрешённых классов, клонирование урока.
- Журнал: одинаковое соотношение 2:3 у всех карточек и состояний, фиксированная геометрия при длинном имени, корректные фильтры и избранные, отсутствие боевых показателей.
- Файлы: нет base64/BLOB в игровых таблицах, все asset ID разрешаются, отсутствующая картинка показывает заглушку; у карточек непрозрачный фон и единый 2:3, у пака и аксессуаров проверена альфа; каталог предыдущей версии пригоден для отката.
- UI: 360 px телефон / планшет / 1366 px ноутбук, Tab/Enter, отключённая анимация, отсутствие точечных мелких целей на телефоне, отсутствие игровых элементов у остальных аккаунтов.
- Регрессия: существующий набор тестов core и релевантные JS-проверки; проверка `collectstatic` после перехода на STORAGES; учебные логины, квизы, кодинг, игры, экзамены и гостевой вход.

Пять конкурентных тестов находятся в `tower/tests/test_wallet_concurrency.py`: первое создание, одинаковое начисление, разные начисления, конкурирующие списания, подмена получателя с одним UUID. На SQLite они явно пропускаются. Для повторения проверки использовать отдельный локальный PostgreSQL с правом создания тестовой БД. ### Выкатка и откат

1. Создать резервную копию БД; загрузить версию графики и проверить manifest.
2. Применить добавочные миграции с выключенными разрешениями; проверить обычные аккаунты.
3. Включить TOWER_ENABLED, назначить одного учителя, включить один негостевой класс.
4. Пройти полный сценарий: учебная награда → пак → сборка → карточка в журнале → аксессуар → профиль/присутствие.
5. Проверить историю, отсутствие дублей, ошибки и время загрузки; сравнить доход за неделю со стоимостью пака и аксессуаров.
6. При проблеме выключить TOWER_ENABLED; не удалять таблицы/проводки/ассеты. Для отката кода использовать версию, совместимую с добавленной схемой.

- Папка с результатами генерации по стабильным именам из ART_PROMPTS.md.

Эти сведения не нужны для начала этапа 1. Настройки существующего DNS и Render из кода не подтверждены; перед изменениями проверить фактическую инфраструктуру.

## 12. Как включить реализованный этап 1

1. При обновлении сервера выполнить `python manage.py migrate`. Миграция `core.0034_tower_access` добавляет оба переключателя с `False` и ограничение, запрещающее включать башню для гостевого класса.
2. Задать серверную переменную окружения `TOWER_ENABLED=true` и перезапустить процесс приложения. По умолчанию выключено. Административное назначение прав возможно и до включения общего флага.
3. Войти в `/admin/` как Django superuser, открыть нужного Teacher и отметить «Управление башней». Обычный staff с правом редактирования учителей не может изменить эту галочку даже поддельным POST.
4. Войти под назначенным учителем, открыть новый пункт «Башня» (`/teacher/tower/`) и отметить «Доступ учеников к башне» для собственного обычного класса. Сохранить. Superuser также может включить доступ в карточке класса админки; владелец класса должен быть активным и назначенным.
5. У учеников появится ссылка на `/tower/` в кабинете и на странице урока. Пока это страница подготовки коллекционного журнала. Назначенному учителю и superuser доступен `/teacher/tower/preview/` без создания ученического аккаунта/кошелька. Названия маршрутов и полей `tower` сохраняются для совместимости с завершённым этапом 1.
6. Для выключения отдельного класса снять галочку, для отзыва учителя снять его право, для общей остановки задать `TOWER_ENABLED=false` и перезапустить приложение. Права проверяются заново на каждом запросе; повторный вход пользователя не требуется.

### Если назначенный учитель видит отказ

- Галочка Teacher.can_manage_tower не включает общий сервис. Сначала проверить `TOWER_ENABLED=true` у работающего процесса. В Render: сервис сайта → Environment → добавить/обновить переменную → **Save and deploy**. **Save only** сохранит значение без применения до следующего деплоя ([документация Render](https://render.com/docs/configure-environment-variables)).
- На включённом сервисе нужно войти именно как Teacher через `/teacher/login/`; обычный Django staff-вход в `/admin/` не является сессией учителя. Superuser имеет собственный административный допуск. Нельзя подменять эту проверку поиском учителя по имени пользователя Django.
- После обновления кода HTML отличает общий выключатель, отсутствие права и отсутствие учительской сессии. В списке/карточке учителей администратор видит предупреждение, если общий сервис выключен. API сохраняет коды `tower_disabled`, `tower_access_denied`, `not_authenticated`.
- Для `/teacher/tower/preview/` не требуется включать какой-либо класс: это предпросмотр назначенного активного учителя или superuser. Галочка класса относится к ученикам.

API этапа 1:

- `GET /api/tower/status/` — допуск текущего ученика и список его разрешённых классов.
- `GET /api/teacher/tower/classes/` — классы, которыми вправе управлять текущий назначенный учитель; superuser видит все.
- `PATCH /api/teacher/tower/classes/<id>/` с JSON `{"tower_enabled": true}` или `false` — изменение допуска; обязательна CSRF-защита.

Обычные API создания/переименования классов не меняют игровые переключатели. HTML-страницы башни и API не кэшируются. Учительские переключения класса и изменения прав через админку записываются в TowerAuditEvent; операции с валютой связаны с проводкой, автором, причиной и предыдущим/новым остатком. Стандартный журнал Django admin также сохраняется.

В локальной SQLite перед применением миграций создана резервная копия в `artifacts/tower/before-step1-20261019T180743188412Z.sqlite3`; применены также существовавшие в проекте более ранние неприменённые миграции. Серверная БД и DNS не изменялись.
